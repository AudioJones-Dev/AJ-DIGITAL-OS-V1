# AJ Digital OS Intake Event Model

**Status:** architecture model specification
**Date:** 2026-07-03
**Owner:** AJ Digital OS engineering
**Scope:** website-originated lead and diagnostic event intake into AJ Digital OS
**Decision level:** documentation only. No endpoint, migration, runtime wiring, CRM write, n8n workflow, HubSpot sync, UI, storage, or production change is authorized by this document.

## 1. Purpose

Define how website-originated lead and diagnostic events enter AJ Digital OS safely, idempotently, traceably, and without creating duplicate CRM, project, onboarding, deliverable, or reporting records.

This model exists to protect four boundaries:

1. `audiojones-clean` may request intake.
2. AJ Digital OS decides canonical CRM state.
3. No website event directly creates a project.
4. No orchestration tool becomes source of truth.

This is the missing layer between the pushed website handoff contract and future implementation:

```txt
signed event
-> validated intake record
-> idempotency check
-> tenant resolution
-> source reference
-> CRM adapter decision
-> receipt/dead-letter
```

## 2. Source Systems

Approved source system:

| Source system | Role | Canonical ownership |
| --- | --- | --- |
| `audiojones-clean` | Public website lead and diagnostic source | Website form submissions, diagnostic sessions, score/report snapshots, attribution at capture, handoff requests |

Future possible source systems must be approved separately. Do not silently let n8n, HubSpot, PostHog, Metabase, or a portal become a source system for this contract.

Allowed website-originated event families:

| Event | Meaning |
| --- | --- |
| `website.lead_captured` | A website lead source record exists |
| `website.diagnostic_started` | A diagnostic session started |
| `website.diagnostic_completed` | A diagnostic result/report snapshot exists |
| `website.booking_clicked` | A visitor expressed booking intent |
| `website.handoff_requested` | Website requests AJ Digital OS operational intake |
| `website.suppression_updated` | Website source consent/suppression changed |

Only `website.handoff_requested` should be allowed to create or link operational CRM objects in the first implementation. Other events can be stored for analytics, attribution, or later enrichment.

## 3. Receiving System

AJ Digital OS is the receiving system.

Receiving responsibilities:

- verify source authenticity
- validate event shape
- apply idempotency
- store intake state
- resolve tenant
- enforce consent and suppression rules
- create or link CRM records through service contracts
- record source references
- emit audit and attribution
- return durable receipts
- dead-letter ambiguous or unsafe events

AJ Digital OS must not:

- scrape `audiojones-clean` database tables
- accept direct website writes into CRM tables
- create projects directly from website events
- let n8n own retry/idempotency state
- let HubSpot become canonical CRM state
- store secrets, raw credentials, or private payload dumps in the public repo

## 4. Event Envelope

Every intake event must use a stable envelope.

```json
{
  "eventId": "uuid",
  "eventType": "website.handoff_requested",
  "schemaVersion": 1,
  "occurredAt": "2026-07-03T00:00:00.000Z",
  "sourceSystem": "audiojones-clean",
  "environment": "production",
  "correlationId": "uuid-or-stable-trace-id",
  "causationId": "optional-upstream-event-id",
  "source": {
    "leadId": "website-lead-id",
    "diagnosticSessionId": "optional-session-id",
    "diagnosticResultId": "optional-result-id",
    "sourceRoute": "/diagnostics/founder-intelligence"
  },
  "actor": {
    "type": "website_visitor",
    "id": "anonymous-or-known-visitor-reference"
  },
  "data": {}
}
```

Required envelope fields:

| Field | Rule |
| --- | --- |
| `eventId` | Required UUID or approved stable unique ID. Used for event-level idempotency |
| `eventType` | Required known event family |
| `schemaVersion` | Required integer. v1 changes are additive only |
| `occurredAt` | Required ISO-8601 UTC timestamp from source system |
| `sourceSystem` | Must equal `audiojones-clean` for this model |
| `environment` | Required environment label |
| `correlationId` | Required when available; generated by receiver if missing in first implementation |
| `causationId` | Optional upstream event ID |
| `source` | Required source references |
| `actor` | Required actor shape; may be anonymous |
| `data` | Required event-specific payload |

Rejected envelope conditions:

- missing `eventId`
- unknown `sourceSystem`
- unknown `eventType`
- unsupported `schemaVersion`
- malformed timestamp
- PII in URL/query string rather than signed body
- payload contains secrets, tokens, credentials, private exports, or binary deliverables

## 5. Idempotency Rules

Idempotency must happen before CRM writes.

Primary idempotency key:

```txt
sourceSystem + eventId
```

Secondary source-reference keys:

```txt
sourceSystem + source.leadId
sourceSystem + source.diagnosticSessionId
sourceSystem + source.diagnosticResultId
tenantId + sourceSystem + sourceObjectType + sourceObjectId
```

Rules:

1. Duplicate `sourceSystem + eventId` returns the prior receipt outcome.
2. Duplicate `source.leadId` inside the same tenant links to the existing CRM source reference.
3. Duplicate `source.leadId` across possible tenants is not auto-merged; it goes to review.
4. A later `website.diagnostic_completed` may enrich an existing lead only through source-reference mapping.
5. CRM primary keys are not sufficient for idempotency because website source IDs and OS CRM IDs are different identity domains.
6. Retries must not create duplicate contacts, companies, leads, opportunities, tasks, workflows, deliverables, or receipts.

Recommended first persistence shape:

```txt
website_intake_events
```

with a unique index on:

```txt
(source_system, event_id)
```

Recommended source reference shape:

```txt
crm_source_refs
```

with a unique index on:

```txt
(tenant_id, source_system, source_object_type, source_object_id)
```

## 6. Source Reference Model

Source references connect source-system facts to OS-owned operational records.

They are not CRM truth by themselves.

Recommended logical model:

```txt
crm_source_refs
```

Suggested fields:

| Field | Purpose |
| --- | --- |
| `tenant_id` | Tenant boundary after resolution |
| `source_ref_id` | OS-generated source reference ID |
| `source_system` | `audiojones-clean` |
| `source_object_type` | `lead`, `diagnostic_session`, `diagnostic_result`, `booking_event`, `suppression_event` |
| `source_object_id` | Source system object ID |
| `target_object_type` | `contact`, `company`, `lead`, `opportunity`, `client`, `workflow`, `deliverable`, `report` |
| `target_object_id` | OS-owned object ID |
| `event_id` | Intake event that created or updated the reference |
| `correlation_id` | Cross-system trace ID |
| `created_at` | First link timestamp |
| `updated_at` | Last link timestamp |
| `metadata` | Redacted, non-secret, non-authoritative context |

Source-reference rules:

- A source reference can point to an OS CRM object.
- A source reference can point to a workflow/report later, after OS creates it.
- A source reference must not make the website source record canonical inside OS.
- HubSpot IDs, if approved later, are external refs only and should not replace OS target IDs.
- Source refs must be tenant-scoped before they can affect CRM state.

## 7. Intake Receipt Model

Every intake attempt should produce a durable receipt.

Receipt events:

| Receipt | Meaning |
| --- | --- |
| `ajos.handoff_accepted` | OS accepted the event and created or linked downstream refs |
| `ajos.handoff_rejected` | OS rejected the event with a safe reason code |
| `ajos.handoff_needs_review` | OS parked the event for operator review |
| `ajos.handoff_duplicate` | OS received a duplicate and returned the original outcome |
| `ajos.report_ready` | OS later produced a report or deliverable projection |

Recommended receipt fields:

| Field | Purpose |
| --- | --- |
| `receiptId` | OS receipt ID |
| `sourceEventId` | Website event ID |
| `sourceSystem` | `audiojones-clean` |
| `tenantId` | Resolved tenant, when available |
| `status` | `accepted`, `rejected`, `needs_review`, `duplicate` |
| `reasonCode` | Safe machine-readable reason |
| `contactId` | Optional OS CRM contact |
| `companyId` | Optional OS CRM company |
| `leadId` | Optional OS CRM lead |
| `opportunityId` | Optional OS CRM opportunity |
| `sourceRefIds` | Created or linked source refs |
| `createdAt` | Receipt timestamp |
| `correlationId` | Trace ID |

Safe reason codes:

- `accepted`
- `duplicate_event`
- `invalid_signature`
- `unsupported_schema_version`
- `unknown_event_type`
- `tenant_unresolved`
- `tenant_ambiguous`
- `consent_missing`
- `suppressed_contact`
- `malformed_payload`
- `crm_write_blocked`
- `operator_review_required`

Receipts should not expose secrets, raw stack traces, private client data, or sensitive payload fragments.

## 8. Dead-Letter Handling

Dead-letter records are required for authenticated events that cannot safely proceed.

Dead-letter conditions:

- tenant cannot be resolved
- tenant resolution is ambiguous
- source event is valid but unsupported
- consent is missing or conflicts with requested action
- source contact appears suppressed
- source lead ID maps to conflicting OS records
- company/contact matching is ambiguous
- CRM write is blocked by permissions or approval policy
- schema version is valid but not yet supported by the implementation

Recommended statuses:

| Status | Meaning |
| --- | --- |
| `received` | Event stored but not processed |
| `validated` | Envelope and payload validation passed |
| `duplicate` | Event already processed |
| `tenant_pending` | Tenant resolution needs review |
| `blocked` | Policy/consent/security blocked processing |
| `dead_lettered` | Event cannot proceed without manual action |
| `accepted` | Event completed intended action |
| `rejected` | Event safely rejected |

Dead-letter rules:

- Dead-lettering is not failure; it is a safe holding state.
- Dead-letter records must preserve enough metadata to replay after operator correction.
- PII must be redacted or access-controlled.
- A dead-letter replay must reuse original source IDs and idempotency keys.
- n8n must not become the dead-letter store of record.

## 9. Deduplication Logic

Deduplication occurs in layers.

### Layer 1 - Event Deduplication

Check:

```txt
sourceSystem + eventId
```

Outcome:

- duplicate event returns existing receipt
- no CRM writes
- audit duplicate if useful

### Layer 2 - Source Reference Deduplication

Check:

```txt
tenantId + sourceSystem + sourceObjectType + sourceObjectId
```

Outcome:

- link to existing OS target object
- do not create new CRM record

### Layer 3 - CRM Object Matching

Check tenant-scoped object candidates:

- contact email
- contact phone
- company domain
- company name
- existing lead source reference
- existing opportunity source reference

Outcome:

- exact safe match: link/update according to policy
- multiple candidates: dead-letter for review
- no candidate: create through CRM service contract

### Layer 4 - Operational Boundary Deduplication

Do not create project/onboarding/deliverable records from website events.

Only OS-approved downstream state changes can create:

- client account
- workflow/mission
- project-equivalent object
- deliverable
- report

## 10. Contact/Company Matching

Matching must be tenant-scoped.

Forbidden:

```txt
global email lookup
global phone lookup
global company domain lookup
cross-tenant auto-merge
```

Allowed after tenant resolution:

| Input | Matching rule |
| --- | --- |
| email | tenant-scoped exact normalized email |
| phone | tenant-scoped normalized phone |
| company domain | tenant-scoped normalized domain |
| company name | tenant-scoped normalized name with review fallback |
| source lead ID | source-reference lookup |

Company support gap:

The current CRM foundation includes `crm_companies` and a `CrmCompany` type, but company service/store support still needs to be added before intake can safely create or link companies through canonical CRM contracts.

First implementation rule:

If company service support is not ready, do not write company rows directly. Store company data in the intake event/source-reference context and create contact/lead only if approved.

## 11. Lead/Opportunity Creation Rules

Website events request intake. AJ Digital OS decides state.

### Lead Creation

Lead creation is allowed when:

- event is authenticated
- payload is valid
- tenant is resolved
- consent policy allows intake
- source reference does not already map to a lead
- contact matching is safe
- CRM service permissions allow the write

Lead creation must use the CRM service contract.

Suggested default lead fields:

| CRM field | Source |
| --- | --- |
| `tenantId` | tenant resolution |
| `leadId` | OS-generated ID or approved deterministic ID |
| `contactId` | matched or created contact |
| `companyId` | matched or created company when supported |
| `status` | `new` or approved intake status |
| `source` | `audiojones-clean` |
| `score` | normalized 0-100 score only |
| `urgency` | mapped from routing priority |

### Opportunity Creation

Opportunity creation is allowed only when qualification rules pass.

Possible qualification inputs:

- diagnostic priority
- normalized score threshold
- booking intent
- route-specific offer fit
- operator approval
- existing pipeline policy

Opportunity creation is not allowed when:

- consent is false or suppressed
- tenant is unresolved
- lead fit is low and no booking intent exists
- default pipeline/stage is not configured
- duplicate source reference exists for an opportunity

Required before implementation:

- approved default pipeline
- approved default stage
- approved source-reference strategy
- approved qualification threshold

## 12. Project Creation Boundary

No website event should directly create a project.

Reason:

Project/onboarding state is operational execution state. Website events are acquisition/source facts. Collapsing those layers would recreate the same failure mode as diagnostic sprawl: duplicated state, unclear ownership, and premature workflow branching.

Allowed first-stage outcome:

```txt
website.handoff_requested
-> contact/company/lead
-> optional opportunity
-> optional workflow intent or operator review
```

Not allowed from website event alone:

```txt
create project
create onboarding workflow
create deliverable
publish report
create client-facing task
trigger outbound automation without consent and policy checks
```

Project boundary decision still required:

| Candidate | Notes |
| --- | --- |
| `missions` | Existing OS workflow concept |
| `mission_runs` | Execution/run metadata, not necessarily project truth |
| portal `projects` projection | Client-facing presentation concept in portal contract |
| future OS `projects` table | Not approved yet |
| workflow wrapper | Possible first implementation without new table |

Until this is resolved, intake should stop at CRM lead/opportunity plus review/workflow intent.

## 14. Retry Rules

Retry behavior must be safe by default.

Source retry:

- `audiojones-clean` may retry the same event using the same `eventId`.
- AJ Digital OS must return the same receipt for duplicate `eventId`.

Receiver retry:

- AJ Digital OS may retry internal processing only when the prior state is retryable.
- Retry state must be stored in the intake event model, not only in n8n.

Retryable states:

- transient CRM store unavailable
- transient attribution writer unavailable
- transient receipt dispatch unavailable
- tenant rule temporarily unavailable

Non-retryable states without operator action:

- invalid signature
- malformed payload
- unsupported source system
- consent blocked
- tenant ambiguous
- duplicate source reference conflict
- suppressed contact

Backoff:

- first retries should use short exponential backoff
- after maximum attempts, mark `dead_lettered` or `needs_review`
- retries must preserve source IDs, event IDs, and correlation IDs

## 15. Security Constraints

Security requirements:

- no Firebase
- no hardcoded secrets
- signed server-to-server event delivery
- replay protection with timestamp and nonce
- fail closed on invalid signature
- payload schema validation before mutation
- tenant resolution before CRM write
- tenant-scoped matching only
- no PII in URLs
- no raw payload dumps in public repo
- no secrets or credentials in logs
- no n8n-owned lifecycle truth
- no HubSpot-owned canonical truth
- no direct website database reads by OS
- no direct website writes into OS tables

Reserved secret names only:

```txt
AUDIOJONES_CLEAN_TO_OS_WEBHOOK_SECRET
AUDIOJONES_CLEAN_WEBHOOK_MAX_SKEW_SECONDS
AUDIOJONES_CLEAN_WEBHOOK_REPLAY_TTL_SECONDS
```

Do not commit values for those names.
